## Session (flatpickr hardening) — PR #49

- **PR #49 — Make the flatpickr dd/mm/yyyy picker actually robust with Livewire**: the PR #48 flatpickr loader was NOT safe — three real problems: (1) `Livewire.hook('commit')` was registered INSIDE a `livewire:navigated` listener, so it never ran on full page loads and stacked (re-registered) on every SPA navigation; (2) flatpickr's `altInput` injects a sibling node that a Livewire morph would destroy/duplicate (date flicker / revert to Y-m-d / broken widget), and the `el._flatpickr` guard then blocked re-init of the now-broken instance; (3) `allowInput:true` let manual typing bypass the Livewire sync. Fixes:
  - Loader rewritten: init `.datepicker:not([data-fp-ready])` (attribute guard), `altInput/altFormat:"d/m/Y"/dateFormat:"Y-m-d"`, `disableMobile`, dropped `allowInput`; explicit `onChange` writes `Y-m-d` back to the real input and dispatches `input`+`change` so Livewire always captures it. Registered ONCE: `DOMContentLoaded` + `livewire:init` (which also registers a single `Livewire.hook('morph.updated')` to init newly-appeared pickers) + `livewire:navigated`. No stacking.
  - Every `.datepicker`'s wrapping `.input-group` now has `wire:ignore` so Livewire never morphs the flatpickr DOM. Covers the 6 inputs incl. the two conditionally-rendered ones (completion_date under UnderConstruction/OffPlan status; lease_expiry_date under has_leasehold) — those get initialised by the `morph.updated` hook when their `@if` first renders.
  - Trade-off (acceptable): with `wire:ignore`, a server-side value change (resetForm) won't repaint the field; initial values still render on first paint and the user drives it afterward — standard flatpickr+Livewire pattern.
  - JS still can't run in the sandbox → MUST verify in a browser after deploy: open add/edit property, toggle status to Under Construction and the leasehold switch (confirm completion_date/lease_expiry_date pickers appear and work), pick dates (see dd/mm/yyyy), save, reopen (value persists, stored Y-m-d). ## Session (flatpickr init timing fix) — PR #50

- **PR #50 — Datepicker wasn't initialising ("ga bisa")**: client reported the picker didn't work. Diagnosis: the PHP data path is CORRECT — `PropertyEditForm::set()` hydrates `availability_date`/`visit_date`/`completion_date`/`lease_expiry_date` as `->toDateString()` (`Y-m-d`), and `PropertyService` create/update receive `Y-m-d` via `wire:model` (validation `date_format:Y-m-d` passes). So NO `->format('Y-m-d')` is needed in JS and the service DOES get the data. The failure was purely JS init timing: the loader relied on `DOMContentLoaded`/`livewire:init` which can have already fired by the time the deferred `@push('script')` block executes at the bottom of body, so `initDatepickers()` never ran. Confirmed every page (public + CMS) uses the same layout `layouts::app` (config/livewire.php `component_layout`), which renders `<x-vendors />` + `@stack('script')` + `@livewireScripts` in that order — so flatpickr loads fine, the issue was only the init trigger.
  - Fix: call `window.initDatepickers()` DIRECTLY at the end of the pushed script (DOM is already parsed since the block sits before `@livewireScripts` at body end), keep `livewire:navigated` re-init, and register the `morph.updated` hook idempotently (`window.datepickerMorphHookRegistered` guard) via either `livewire:init` or an immediate `if (window.Livewire)` check — no stacking, no dependency on a possibly-missed event. `wire:ignore` wrappers + `data-fp-ready` guard from PR #49 unchanged.
  - STILL needs a browser smoke test after deploy (JS can't run in sandbox). Full suite 76 passed.

## Session (datepicker root cause: Livewire 4 + wire:ignore) — PR #51

- **PR #51 — THE real datepicker fix (value "ga ke ambil")**: previous flatpickr attempts failed because of a wrong mental model of the stack. Verified facts: Livewire is **v4.4.8** (not v3). Per Livewire 4 docs, `wire:ignore` makes Livewire ignore that DOM, so a `wire:model` inside `wire:ignore` is NOT read back on commit — which is exactly why the picked date never reached the component ("data tidak ke-ambil"). The project already had the correct pattern in `components/form/trix.blade.php`: `wire:ignore` + Alpine `x-data`/`x-init` + `$wire.set('{{ $model }}', ...)`, reading the initial value via `@js(data_get($this, $model))`.
  - New reusable component `resources/views/components/form/datepicker.blade.php`: `wire:ignore` + `x-init="flatpickr($refs.datepicker, { altInput:true, altFormat:'d/m/Y', dateFormat:'Y-m-d', disableMobile:true, defaultDate: @js(data_get($this, $model) ?: null), onChange: dateStr => $wire.set('{{ $model }}', dateStr, {{ live?true:false }}) })"`. Props: `model, id, min, max, required, disabled, live`. `live=false` (deferred `$wire.set(..., false)`) for form fields; `live=true` for list filters so the query refreshes immediately (replacing the old `wire:model.lazy`).

Because each component self-inits via Alpine `x-init`, the conditionally-shown completion_date/lease_expiry_date init correctly when their block renders — no global init/`morph.updated` hook needed.
  - Flatpickr loader reverted to just loading the asset (CSS+JS); the global `.datepicker` auto-init + hooks removed (component owns init now). `flatpickr.js` is a sync `<script src>` in `@stack('script')` which runs before `@livewireScripts`/Alpine boot, so `window.flatpickr` exists when `x-init` fires. All pages use layout `layouts::app`.
  - Display dd/mm/yyyy (altInput); stored/validated value stays `Y-m-d` (forms hydrate `->toDateString()`, service already receives `Y-m-d` — NO JS reformat needed; the PHP path was always correct).
